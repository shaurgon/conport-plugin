# conport changelog

## 22.0.0

**Breaking: the server refuses ordinary growth past the epic ceiling; update
the plugin and the `conport` CLI together.** Older plugins file defects as
ordinary tasks and fail with `409 epic_growth_ceiling` when the ceiling is
reached; older CLI versions do not know Bug or the `kind: bug` plan label.
Every `conport` CLI command the plugin, its docs and the server's model debts
tell an agent to run now names `npx -y conport@^0.8.0`, up from `^0.7.3`: CLI
0.8.0 is the first release that knows Bug and the `kind: bug` plan label.

Plan sections labelled `kind: bug` create defects; the execution contract files defects with `kind='bug'` and follows the server prescription when an ordinary finding exceeds the epic growth ceiling.

Skills file confirmed defects as `kind='bug'` and polish or new work as
`kind='task'`. The server counts the epic growth ceiling; on
`epic_growth_ceiling`, execute the call in `suggestions[].call` for the tails
epic it names. Read `epic_progress.plan_tasks`, `ordinary_added`, `bugs` and
`growth_ceiling`; `growth_ceiling: null` means no ceiling. With a ceiling, the
server summary reads "ordinary after plan N of C, bugs B". The workflow run
summary reads "ordinary tasks added N of ceiling C; bug fixes B", or
"ordinary tasks added N (no ceiling); bug fixes B" outside that scope.
The Stop hook reads the epic’s `epic_progress` and marks growth only when
`ordinary_added > 0` and `growth_ceiling` is not null. Bugs stay visible as
open work without contributing to the growth marker.
Open Bugs and their epics lead `backlog.top` across milestones, ahead of
ordinary work of the current milestone; routine selection keeps that order
and its eligibility, readiness and review gates.

Workflows file confirmed defects as bugs and read the epic growth counters from the server. Ordinary findings refused by the ceiling go to the release tails epic, including the task workflow's Minor umbrella.

Bug is now a task kind across MCP, REST, the CLI, the dashboard and the Orca
panel. It follows the same review journal, time accounting, estimates and
hierarchy as an ordinary leaf. `has_open_bug` puts open Bugs and their epics
first without changing `effective_priority`. `conport task list` lists open
`task` and `bug` leaves outside epics in server order and marks Bugs; the Orca
panel preserves that order with a Bug label. `conport plan import` creates Bugs
from sections labelled `kind: bug`.
For all projects, the server enforces the growth ceiling on release epics
whose plan started after rollout. `epic_progress` exposes `plan_tasks`,
`ordinary_added`, `bugs` and `growth_ceiling` (null outside that scope), in
write echoes and epic reads; clients use these counters instead of recounting.
The refusal's ordered suggestions create a missing tails epic with `priority=1`
and file the work there. Its next milestone must be a release milestone;
otherwise `next_milestone` is null. Whenever the target tails epic has no
milestone, whether found or created, `ask_user_milestone` asks where it belongs.
The skills, the plan contract and the epic task of the Orca plugin file the
tails epic of the release one way. It is filed with priority 1. Inspect the next open milestone after the release: if it is a release, find the oldest open tails epic with the exact title in that milestone, or create it there; otherwise find or create it without a milestone, file the work, and ask the user which milestone it goes to. A defect task is no longer marked
by `The gap: ` at the start of its description: its kind `bug` says so, and
the epic workflow no longer counts growth itself.

The rest of the refusals of the link tools carry a code, the same on REST and on MCP, in front of one sentence that names the one thing to do. A link type outside its list — `relationship` of `link_items` and `get_linked`, `link_type` of `link_project` and `unlink_project`, and the REST `link_type` of `POST`/`PUT /links` and `POST`/`DELETE /project-links` — is `invalid_relationship`, instead of an argument validation dump on MCP and a generic 422 on REST. A `direction` of `get_linked` or `get_project_links` outside outgoing, incoming, both is `invalid_direction`. A project linked to itself is `same_project`, and a deletion of a project link that does not exist is `project_link_not_found`. On MCP each refusal reads `<code>: <sentence>`.

Breaking for REST clients: `GET /project-links` answers a `direction` outside its list with 422 `invalid_direction` instead of 400 with a string, and `POST /project-links` (400 `same_project`) and `DELETE /project-links` (404 `project_link_not_found`) give `detail` as an object with `error` and `message` instead of a string.

The background check of a portion drops a finding you dismissed under another spelling too, of the same `subject` and `kind`: arrows and colons aside (`FACT :Entity → :Entity` is `FACT Entity → Entity`), and an entity written `X (y)` with `y` as code (it holds `_`, `/`, `.` or `{}`) taken for the whole `X` or the whole `y` — `agent_event` goes with `Agent event (agent_event)`. A plain word in brackets makes another thing (`API_HOST (agent)` is not `API_HOST`), as do two wrapped names sharing only a part, a word more or less and another end of a relation; a relation — `Source type Target` or `Source → Target` — is never unwrapped, and such a finding stays. `X (y)` is unwrapped, on either side, for a `missing` finding only: an `invented` finding and its dismissal both name entities the portion holds and are compared by their whole names, so `cli/conport` and `Точка входа (cli/conport)` never take each other there. The `mismatch` debt and the refit of stored findings read dismissals the same way. The conport skill says that a finding about a relation is dismissed as an entity named `Source type Target`: `relation` is no subject.

## 21.0.0
Breaking: the nine tools of the entity graph and the semantic pass are retired — `entities`, `entity`, `entity_related`, `communities`, `community`, `graph_stats`, `semantic_pass_run`, `semantic_pass_stats` and `semantic_cleanup`. A call answers one hint: use the project model instead (`arch_names`, `arch_entity`, `arch_lookup`); the server keeps running the semantic pass itself. The tool-profile groups `graphrag` and `semantic` are accepted and list nothing until the next major release. Their REST routes (`/api/v1/graph/*`, `/api/v1/projects/{project}/graph`, `/api/v1/projects/{project}/semantic/*`) answer 410 with the same action, the dashboard has no graph page, the project export carries no graph sections (`schema_version` 5), and `conport api graph|semantic` answers with the hint. Every number of the entity graph came from a counter shared by the whole service, which is the reason they go.

No surface answers or takes a row number drawn from a counter shared by the whole service any more; every item is addressed inside its project. A context version is named by `context_type` and `version`, a custom-data entry by `category` and `key`: `item_history` takes `item_type='context'` with `context_type` and `version`, or `item_type='custom_data'` with `category` and `key`, and refuses `item_id` for them with one action; context answers and `context_history` carry no `id`. A link between items keeps a number inside its project, so `get_linked` shows small numbers that restart in every project; a number handed out before this release no longer finds its link. A cross-project link is named by its two projects and its type: `unlink_project(project, target_project, link_type)` replaces `link_id`, which is refused with one action, and `get_project_links` lists links by those three. `add_linked_task` and `get_block_backlinks` answer without `link_id`; `gap_list` carries no `context_id`. The command list in `references/command_list.md` shows the new addresses.

Every command the skills, their references, the docs, the commit guard and the `/conport:epic` workflow tell an agent to run now names the `conport` CLI as `npx -y conport@^0.7.3`. With the range `^0.7` npx took a cached 0.7.0, which has no `arch` command and answered `arch check` and `arch submit` with `unknown command 'arch'`; 0.7.3 is the first release with `arch`. The actions of the model debts `check_stale` and `removed_but_present` in the server's answers, and their mirror in the skill, name `npx -y conport@^0.7.3 arch check` too. The CLI 0.7.4 also exits 1, not 0, when it shows its help because a command group was run without its subcommand or the CLI without a command.

The Kind field of the Agent report form is a text input, so the form link fills it. The output format of `add_milestone` and `update_milestone` names a milestone as `milestone-<id>` and never by its position in the roadmap.

`render_current_architecture` shows only the decisions in force: a decision absorbed into a pattern, deprecated or superseded stays out of the render, as `list_decisions(only_current=true)` leaves it out.

A decision absorbed into a pattern is no longer `current`: `get_decision`, `list_decisions`, `search` and the decisions of an `arch_entity` card (and of the REST card of an entity) give it `superseded`. The read surfaces name the patterns that absorbed it in the new field `superseded_by_patterns`, and each decision of the card now names what replaced it, as `get_decision` does: `superseded_by` lists the decisions that supersede it and `superseded_by_patterns` the patterns it was absorbed into, each null when there is none. The conport skill's *Decision currency* follows `superseded_by` to a decision or `superseded_by_patterns` to a pattern.

`get_linked` pages by link number: `after` returns the links numbered above it, and the answer's `next_after` starts the next page, null on the last one. The REST `GET /links` pages the same way with `after` and `next_after`; `limit` and `offset` still work as before. While links are being written or deleted, a walk by `after` returns exactly once every link that existed at its first page and still exists; a link written meanwhile may come back or not.

The REST `GET /links` with `item_type` and no `item_id` gives the links with an end of that type; `item_id` without `item_type` is refused with 422 `item_id_without_item_type`, and a type outside the vocabulary of the link tools with 422.

The background check of a portion keeps only the findings that hold against the portion: a finding in both lists, an invented thing the portion does not have and a missing thing it has are dropped, names compared without case, extra spaces, outer quotes or one closing period, so the `mismatch` debt names fewer, real differences. `arch_status` counts under `unlinked_decisions` only the decisions in force: one absorbed into a pattern is not owed an entity.

The background check of a portion no longer cuts the model's answer about a long document mid-JSON: the answer gets room for 16 384 tokens instead of 4096, so the check stops counting such an answer as off the schema. A check whose attempt failed waits for the nightly retry with its reason: `arch_status` lists it under the new key `retries` (`source`, `reason`, `retry_at` — when the nightly run checks it again), and the `unchecked_portion` blocker of `arch_backfill` gives the same `retry_at`. An answer the LLM still cuts at its limit closes the check `failed` with the new reason `answer_truncated` at once, without a nightly retry; the check in `arch_status` and the blocker carry its one `action`, which splits the document.

The `conport` CLI reads the links of an epic or a document the same way, by `after`, in `plan import`, `plan pull`, `superpowers migrate`, `superpowers relink` and the `epic` commands: a link written or deleted while it reads no longer makes it list a link twice, miss one that was there when it began, or write a link the epic already has a second time.

The background check of a portion shows the model the findings you dismissed, grouped by their reason, and tells it to raise none of them under another name, nor another finding a reason covers just as well; the server still drops a finding only by the same name. A reason written as the class of the finding ("a function, smaller than the model") keeps away the other findings of that class. A request that would pass its size limit with the dismissals is sent without them rather than skipped.

`link_items` and the REST `POST /links` refuse a link to an item the project does not have with `item_not_found` (REST 404) and write nothing; the REST body takes an end type from the vocabulary of the link tools and `document`, which it writes as `doc`; any other word is refused with 422 `unknown_item_type`. The descriptions of `link_items` and `get_linked` say that their schema lists the canonical kinds and that `document` is taken too, as a synonym of `doc`, though the schema does not list it.

`link_items` and `get_linked` take an item type as the REST link routes do: `document` is accepted and read as `doc`, and a type outside the list is refused with `unknown_item_type` and the same sentence REST answers, naming the types to pass, instead of an argument validation dump. A missing end of `link_items`, and a missing entity of `get_linked`, is refused as `item_not_found: <sentence>` or `entity_not_found: <sentence>` — the code and the sentence the REST link routes answer — instead of the bare sentence. An `after` of `get_linked` outside 0 to 2147483647 is refused the same way, as `invalid_page: <sentence>`.

An epic does not bump a version. It writes its changes into the changelog of the unit under `## Unreleased`; the version is bumped once, at the release step, after every epic of the release milestone has merged, and that one bump is the freeze of the release. Parallel epics of one milestone that each bumped shipped diverging numbers. The freeze section of `references/backlog-discipline.md`, the *BACKLOG DISCIPLINE* line of the conport skill and the *Release* section of `conport-roadmap` say so. So do the execution contract `superpowers-conport` writes into a plan and the rules of the epic task of the Orca plugin, so an executor that reads no project instructions gets the rule with the plan.

A finding made after the release epic is frozen at the version bump, and work that can be done right after the push — a live check after the deploy, a dry run on an environment — no longer go to an epic of the next milestone: they go to the tails epic of the release — one per release, filed at the first such finding, attached to the milestone right after the release and taken into work first after the push, before any other milestone. It is filed with priority 1, and only when the open milestone right after the release is a release milestone itself: when it is a standing list (the waiting milestone, the backlog without a date) or there is none, ask the user which milestone the tails go to; the plan contract and the finish mode of `superpowers-conport`, the epic task of the Orca plugin — whose reasons to stop now include that question — and the roadmap page of the docs say so too. It holds no waiting work and is never closed as CANCELLED because it waits; work that waits on another party's service, a date or a measurement window still goes to the waiting milestone, and a defect in this release's code is still closed before the push. The *BACKLOG DISCIPLINE* lines of the conport skill, `references/backlog-discipline.md`, the rules and the *Release* section of `conport-roadmap` and the execution contract `superpowers-conport` writes into a plan say so; the contract no longer lets a finding that must wait be closed as CANCELLED. A filed finding goes to an executor as the next action: a report "after the epic I found N problems" as text, with no task numbers and no work started, is forbidden, and the epic is not ready while one of its findings is open. The red flags of the roadmap skill gain both thoughts. The epic workflow files every finding as a task of the current epic. The epic growth ceiling bounds that: an epic takes max(3, floor(0.3 × plan tasks)) ordinary tasks added after the plan. A defect never counts and always stays in this epic — a review's Critical and Important, a gap hunt's Blocker and Should-fix, a confirmed behaviour defect; polish from findings counts — a review's Minor left after the pass, a task from a Note's answer — and so does new scope. In short, a behaviour defect always stays in this epic; an ordinary finding past the growth ceiling goes to the tails epic of the release, and readiness does not wait for it. The tails epic of the release has one title, `Tails of release <title of the release milestone>`, looked up before one is filed, so a session and the epic workflow never start two. The same rule is carried by the plan contract `superpowers-conport` writes into a plan and by the review agents (`sdd-final-reviewer`, `sdd-gap-hunter`). The epic workflow counts toward the ceiling every child of the epic without a plan section — a task added by hand too — except a child the words of a defect mark; a defect task filed by hand starts its description with `The gap: `, or in an epic with a plan it counts as ordinary work (in an epic without a plan, as one of the tasks the ceiling is measured against). `/conport:task` files the review minors it leaves open as `Review minors left on task-<id>`: a task of the task's epic while its ceiling has room, else a task of the tails epic of the release; a task with no epic has no release milestone, so its minors wait in a progress entry and the person names the milestone; the "Workflow run tails" epic is no longer used.

The finish mode of `superpowers-conport` files a ledger finding under the same ceiling — past it into the tails epic of the release, a new one attached to the milestone right after the release, a defect always into the epic — counts a finding already filed in that tails epic as filed, and reminds in both its reports that the ledger covers neither the final review's findings nor the gap hunt's (Blocker, Should-fix, Note).

`/conport:epic` now needs the tool profile `core,tasks,milestones,documents,arch`, because the workflow calls `list_milestones`; a connection narrowed to the profile of the 20.6.0 entry (`core,tasks,documents,arch`) must add `milestones`. The `superpowers-conport` skill now needs `core,milestones,links`: its finish mode reads `list_milestones` to find the tails epic of the release. `/conport:task` now needs `core,tasks,milestones,documents,links`: its accounting reads `list_milestones` to find the tails epic of the release for the review minors it leaves open. The hooks now need `core,tasks,milestones`: they watch `delete_task`, a tool of the `tasks` group, to drop the cached `[TAILS]` rows, so a connection narrowed to their former profile `core,milestones` must add `tasks`.

The workflows hold the version rule mechanically. Before READY, `/conport:task` (before its merge) and `/conport:epic` (after its last merge) compare every version carrier of the units the project's manifest `.conport/units.json` lists with the base branch, through the helper's new `versions` command. The manifest is the project's, at its repository root, read as of the start of the run: a list of units, each with its carriers — a path, or a directory and a file name, and how its version is read (a field of a JSON file, the first group of a regular expression, or `metadata.version` of a skill). A project without the manifest has no comparison: the run passes and says so in one note; a manifest that cannot be read refuses READY with "Fix .conport/units.json, then run again: …". A difference refuses READY with one action, "Restore the version of <unit> as <base> has it; units are raised only at the release step.": a task run fails with `VERSION_RAISED` and merges nothing (a head a rebase made is checked again before its merge), an epic run files the action as an unmet criterion of its goal. The release step is not run through either workflow, and the roadmap skill says so: when the default branch is ahead of the published one at the start of a run and already differs from it — a release step not pushed yet — the action is "Push the release step first, then run again: …" (`RELEASE_NOT_PUSHED`), never a restore; when it is behind the published one or diverged from it — a release pushed from another checkout — the action is "Update the default branch from origin/<branch> first, then run again." (`BRANCH_BEHIND_ORIGIN`). In both cases an epic run asks you instead of filing a child. A check that does not answer, or a carrier whose version neither side can read, refuses READY too.

The Stop hook that holds a turn while an epic the session changed has open children no longer lets the turn end as planned: it says the epic is not done — dispatch the open children now, or name the reason each cannot start. A conport `add_task`, `update_task` or `delete_task` now drops the cached `[TAILS]` rows, so the next message no longer names a child closed or deleted a moment ago as open. Deleting a child of an epic now also marks that epic as changed in this session, so the Stop hook holds the turn while the epic has open children, as it does after `update_task`.

## 20.6.0
A project that lived before its model can now fill it. The conport skill ships the procedure `references/model-backfill.md`, six steps in order: the skeleton of the code, unit by unit, as `code:<unit-name>` sources (no tool of its own builds it); an inventory document "Model backfill: inventory" that gives every document a role; a pass over the documents with a role, oldest first; the things no longer in the code, marked by the portion of "Model backfill: result"; the active decisions attached to entities; and the debts cleared. The user of the project approves the inventory and reads the result; the rollback runs only on the user's word.

A document has a role in the model: `structure` (what exists now), `history` (what has been replaced) or `none` (no portion). `update_document` takes `model_role`, `get_document` and `list_documents` return it and `list_documents` filters by it. A document with the role `structure` or `history` submits a portion whatever its type; the role `none` withdraws the portion of a document, and `history` keeps it and deletes its scenarios. A history source sets no current state and carries no scenarios: a scenario in its portion is refused `scenario_malformed` by the rule `history_source`, and the background check raises no whole-scenario finding for it.

A new tool of the group `arch`, now twelve: `arch_backfill(project, state)` starts (`in_progress`), completes (`completed`) or declines (`declined`) the backfill, with the refusals `backfill_not_ready`, `backfill_not_started` and `backfill_already_started`, each with its action. While the backfill runs, a document with a role and no portion is the debt `no_portion`, and `init` folds those debts into one line, "Backfill: K of M documents submitted" — a notice for a session that does not run the backfill; `arch_status` gives the active decisions without an entity under `unlinked_decisions`, a page at a time with `unlinked_after`. `init` offers the backfill to a project with documents older than its model until it is started or declined: only a session with a person — `init` called with `questions=true` — gets the line that offers it; a routine or a subagent gets the key `offer` alone. The agent shows the offer to the user once; the offer is declined with `arch_backfill(project, state='declined')` after the user declines it. `npx -y conport@^0.7.3 arch withdraw --all` reports every source of the project, and with `--apply` withdraws them all — only on the user's word.

The Superpowers overlay's step *Finish* gains one action: in a project whose model has `code` sources, after an epic that changed the code is merged, submit the skeleton of the units it touched again and run `conport arch check`.

## 20.5.0
The project model gains behaviour. A portion now carries the **scenarios** of its source in `scenarios`, next to its entities and relations: a `sequence` (messages between participants, with `call`, `reply` and `async` steps, an interface `via` and `alt`, `opt` and `loop` bands), a `states` scenario (the life of one thing, with one initial state and the final ones) and an `activity` (a process with decisions, parallel paths and waits, each performer in its own lane). Participants, subjects and performers are entities of the model, named as in `arch_names`; a scenario is grounded in a block of its document or, in a `code:` portion, in a `path` or `symbol` anchor, and belongs to that one source. Without the field the scenarios of a source stay, an empty list deletes them, a list replaces them; a scenario keeps its number under the same name or with `renamed_from`, and `takes_over` moves a scenario of another source to the one that changes that behaviour. Two new tools of the group `arch`, now eleven: `arch_scenarios` lists the scenarios and `arch_scenario` reads one with its participants, states or nodes and steps. `arch_source` gives the scenarios back in the form of a submission, and the card of an entity (`arch_entity`) lists the scenarios it plays a role in.

The write-time check gains eight refusals, each with its one action — `unknown_scenario_kind`, `unknown_node_kind`, `scenario_participant_missing`, `scenario_participant_removed`, `scenario_ref_unknown`, `scenario_malformed`, `scenario_name_taken`, `scenario_too_large` — and the model two debts: `step_without_relation` (a step of a sequence between entities the model does not relate, dismissed with a reason by a one-off record in `dismissed`) and `scenario_participant_gone`; a debt of a scenario carries its `scenario_id`. The background check compares the scenarios of a document portion with the document, and a finding and a dismissal now have `subject` (`entity` or `scenario`) and `where` — the text of a step, or `whole_scenario` for a behaviour the portion has no scenario of. `conport arch check` (CLI 0.7.3, inside the `^0.7` range the skill names) checks the anchors of the scenarios of `code:` portions too.

The conport skill's section *PROJECT MODEL* gains the part *Scenarios*: which kind fits what a document shows, an enumeration against `states`, the fields, the rules of each kind and the limits with how to split a larger scenario, `takes_over` against leaving a repeated behaviour out, a portion with a scenario of each kind, the refusals and debts of scenarios, and a `code:` portion with a scenario and its anchor. When no kind fits, the agent submits no scenario, files a `missing` report as *REPORTING TO THE SERVICE DEVELOPERS* says and dismisses the whole-scenario finding for that reason. The Superpowers overlay submits the scenarios of a spec in the same portion, right after `plan import`. Scenarios need a server of this release: an earlier server refuses a portion with `scenarios` — `arch_submit` as `portion_invalid`, the REST submission and `conport arch submit` with a 422 body-validation error on `scenarios` (`extra_forbidden`).

## 20.3.0
The project model replaces the diagrams. A project now keeps a model of what its system is made of — entities of eight types (`person`, `external_system`, `unit`, `component`, `interface`, `store`, `data`, `setting`) and relations of eight (`contains`, `calls`, `starts`, `reads`, `writes`, `derived_from`, `replaces`, `references`) — built from portions: what one source says, a `spec` or `architecture` document (`doc-N`) or a part of the code (`code:<label>`). The new tool group `arch` holds nine tools: `arch_submit` and `arch_withdraw` write a portion, `arch_source` and `arch_sources` read the portions, `arch_names` lists the names of the model a page at a time, `arch_get` returns a slice of one of four views (`composition`, `neighbourhood`, `contribution`, `data`), `arch_entity` an entity's card, `arch_lookup` the entities at an anchor, and `arch_status` the debts of the model. A refused portion is answered with every error at once, each with its code and one action. The `conport` CLI (`npx -y conport@^0.7`) gains `arch submit`, `arch withdraw`, `arch source` and `arch check`, the local check of the model's anchors against the code, which sends only the outcome. `init` returns the section `arch` — up to five debts of the model, each with its action — when the model owes work. The conport skill gains the section PROJECT MODEL: when to submit a portion, which type a thing takes, the rules of the model, every refusal with its action, the debts of `init`, an example portion of the code for one unit and when to run `conport arch check`; the Superpowers overlay submits the portion of a spec right after `plan import`; a new live-docs page `projects/architecture-model` describes the model. The diagrams are gone: `list_diagrams` is removed and answers with a refusal that points to `arch_get`, documents of the type `diagram` are deleted with the type, and the gap `diagram_stale` is no longer raised. The tool-profile group `diagrams` stays accepted in 20.1.0 as a group that lists nothing, and goes away in 21.0.0. A number outside the 32-bit integer range is answered as a number the project does not have, never as a server error: `arch_entity` and `arch_get` with such an entity or document number refuse with `entity_not_found` and `document_has_no_portion`, a decision of a portion with such a number is `decision_not_found`, `link_items` refuses an end of any kind with such a number with `item_not_found` (an `entity` end with `entity_not_found`), and `get_linked` with such an `item_id` answers an empty list; `get_linked` with `item_id` 0 keeps to that item instead of listing every edge of the project.

A resubmission that drops an entity only its source held while a relation of the portion still names it is refused with `relation_endpoint_missing` and the action to return that entity to `entities` of the portion, which the skill repeats under its table of refusals; an end no source has keeps the action that names `arch_names`.

The `/conport:epic` workflow runs `conport arch check` itself after the last merge of a run, when the project has portions with anchors, and its report carries the outcome under `anchor_check` — the counts the CLI printed, or the command to run by hand when the check could not run; `/conport:epic` now runs on the tool profile `core,tasks,documents,arch`. A document portion over 150 entities is refused with an action the agent can take: move whole units with the entities they contain (or the components of a unit over 150 entities) into a new `architecture` document, submit its portion first with that document's blocks, then the document's portion without those entities but with all their relations and with them in `dismissed`. A `code:` portion over 400 entities is refused with its own action: split it into one label per unit or per component.

An epic is not declared ready while a finding of it is open. Every finding not fixed in the same pass — a gap hunt's Blocker, Should-fix and Note, a review's Critical, Important and Minor — becomes a task of the current epic and is done before the epic is ready; a Note only you can answer is asked at once and the answer becomes the task, and the report names the task numbers instead of listing the findings. The review of a task filed from a finding reports every severity, and its author fixes all of it, Minor included, before that task merges: nothing from it is filed anew or dropped, and only a behaviour defect outside that task's diff becomes a new task. The *BACKLOG DISCIPLINE* lines of the conport skill and `references/backlog-discipline.md` say so, and the release freeze keeps a finding made after the bump as a task of the next milestone's epic. `conport:sdd-gap-hunter` and `conport:sdd-final-reviewer` propose a task — a title and one or two sentences — for every finding, and a gap hunter's Note carries the question to put to you, a column of its findings table. `/conport:epic` gains a findings round before the acceptance: every finding still open becomes a child of the epic. A review minor its fix round left open (one child per task it came from) and each gap the verifier confirmed run the road of a plan task — brief, implementer, review, merge; a Note and a gap nobody could verify are filed with their question and held for you, never run, so the epic stays open until you answer. The reviewer of a finding task is told to report every severity, and a minor it cannot fix holds that task's merge. A finding the run could not give a child holds the epic open, is named under `unfiled_findings` with its brief and question, and is filed at the accounting as a child of the epic, one per finding; a closed child of the same title is never taken for it, and a finding titled like a task the run already knows is handed over under a title of its own. The run ledger lists the children under `findings`, the closing resolution counts the finding tasks and the findings held for you apart from the plan's tasks, and the gap hunter's answer gains `question` for a Note. A held finding's question reaches you through the session that leads the epic in Orca: it asks you each question at once, makes your answer a section of the plan bound to the held task by its marker — or cancels the task when you drop the work — and binds every `unfiled_findings` entry — already filed as a child of the epic — to a plan section the same way, with its brief as the requirement, so the next run executes them and nothing is filed twice; an entry the accounting could not file becomes a section without a marker, and the import creates its task. A held child waits for you on every later run too: by the words `Held for the person:` its description starts with, a run without a plan section for it — `allowNoPlan` included — never hands it to an implementer, and the run summary names it as waiting for the person. In `/conport:task` and `/conport:epic` alike, a review with any open finding, a minor too, is journalled `changes_requested`, and its fix round is a `fix` entry; a minor that round leaves open no longer reads as an approval — the run records it with a `fix` entry and an approving `review` of its own that list the open minors and where they went. No finding is left as a line any more: in `/conport:task` a minor its fix round leaves open is always filed as one follow-up task — a child of the task's own epic when it has one, under the "Workflow run tails" epic otherwise — and in `/conport:epic` it becomes a task of the epic; the `fileMinors` argument is no longer read.

## 16.5.0
